defineWidget.ts

Strong

📁 Files

src/runtime/composables/defineWidget.ts

⚠️ Problem

Concentrates widget registration, validation building, field function creation, and type inference in a single interface. Global registry creates single point of failure and testing bottlenecks.

💡 Solution

Split into separate services: WidgetRegistry (seam for discovery), ValidationStrategy (adapter for validation), FieldBuilder (interface for field creation), and TypeInference (implementation detail). Use dependency injection instead of global registry pattern.

✅ Benefits

  • • Clear seams between concerns (adapter separation)
  • • Better locality - validation logic isolated
  • • Improved testability through dependency injection
  • • Leverage through focused interfaces

⚠️ Problem

CrudService class mixes database operations, business logic, validation orchestration, and hooks. Interface depth issues across multiple CRUD methods.

💡 Solution

Extract repository pattern: CollectionRepository (adapter for data access), ValidationOrchestrator (seam for validation), BusinessRules (interface for CRUD logic), and HookExecutor (implementation detail). Inject dependencies instead of mixed concerns.

✅ Benefits

  • • Better locality - data access isolated from business logic
  • • Improved testability through dependency injection
  • • Leverage through focused CRUD operations

validation.ts

Worth exploring

📁 Files

src/runtime/server/services/validation.ts

⚠️ Problem

`validateAndCoerce` integrates with Drizzle schema generation, validation rules, date coercion, AND custom hooks - interface depth with mixed responsibilities. Split validation approaches create unclear boundaries.

💡 Solution

Strategy pattern: SchemaValidator (adapter for schema generation), RuleValidator (interface for field rules), CoercionEngine (implementation detail), and HookAdapter (seam for custom hooks). Each validator can be composed based on collection configuration.

✅ Benefits

  • • Clear validation strategy separation (interface vs implementation)
  • • Better locality - each validation aspect isolated
  • • Improved testability through strategy composition
  • • Leverage through pluggable validation approaches

📁 Files

src/runtime/server/services/relations.ts

⚠️ Problem

Single module handles configuration validation, payload extraction, and persistence for three storage types (inline, inverse, junction). Storage type entanglement makes them hard to extend and test.

💡 Solution

Extract storage adapter pattern: RelationValidator (interface for validation), PayloadExtractor (seam for extraction), RelationRepository (adapter for persistence). Each storage type can have its own adapter implementation.

✅ Benefits

  • • Clear storage abstraction (adapter pattern)
  • • Better locality - validation separated from persistence
  • • Improved testability through adapter injection
  • • Leverage through pluggable storage strategies

Virtual Module Generation

Worth exploring

📁 Files

src/module.ts

⚠️ Problem

Virtual module generation mixes configuration processing with template generation. `setupWidgets`, `setupBlockComponents`, and collection generation all in same file. Adapter complexity - multiple virtual module types in single module file.

💡 Solution

Extract ModuleGenerator pattern: TemplateEngine (interface for template generation), ConfigProcessor (seam for configuration), and ModuleBuilder (adapter for assembly). Separate concerns for each virtual module type.

✅ Benefits

  • • Clear generation abstraction (adapter pattern)
  • • Better locality - processing separated from generation
  • • Improved testability through dependency injection
  • • Leverage through specialized generators

🏆 Top Recommendation

Recommended Priority: defineWidget.ts

This is the most problematic module with clear architectural friction points. It breaks the deletion test by concentrating excessive complexity in a single interface.

Domain Context: The widget system is foundational to the Collection dashboard configuration - every field in every collection relies on widgets for UI representation and validation.

Architecture Impact: Resolving this will establish patterns for other service modules, improving overall codebase depth and testability.

Why This First

  • • High Impact: All CRUD operations rely on widgets for field rendering
  • • Clear Seams: Separation between registration, validation, and field building
  • • Low Risk: Pure functions, clear interfaces, minimal coupling
  • • High Leverage: One change benefits all collection definitions
  • • Foundation: Establishes patterns for other deep modules
